# Phase 0–9 Delivery and Acceptance Roadmap

**Product:** LumeraVega SMB IN BOX / LF-RISKROSI  
**Revision:** Draft 0.1  
**Status:** Proposed; Product, Security, Legal/Privacy, and Operations approval is outstanding  
**Baseline date:** 2026-10-29

This roadmap converts the repository's current phase-status review into an ordered delivery proposal. It is not an approved product requirements document, compliance assessment, deployment commitment, or production-readiness declaration. Phase 1–4 retain legacy labels where applicable; Phase 5–9 are retrospective groupings. Owners, scope, priorities, and acceptance criteria must be approved before they become release commitments.

## Delivery rules

1. A phase cannot be marked accepted based only on documentation or a local demonstration. Link each claim to the exact source/configuration revision and reproducible test, CI run, or witnessed operational evidence.
2. Record evidence with its owner, revision, environment, date, procedure, result, and retained artifact reference. Mark absent evidence **open**, **unverified**, or **not implemented**—never passed.
3. External decisions (including legal interpretation, hosting/residency, service targets, and operational authorization) require the accountable owner and supporting evidence; code cannot supply that approval.
4. Preserve tenant boundaries, least privilege, data minimization, and explicit error reporting throughout all phases.
5. Phase 9 host enforcement remains **DISABLED** unless all Phase 9 gates are implemented, independently verified, operationally tested, and signed by the accountable owners.

## Current Phase 1–2 implementation notes

- Phase 1 keeps the existing App Router and shared page behavior intact while fixing the containment callbacks' invalid state scope. A larger architecture rewrite remains deferred until the legacy requirements are reconciled and approved.
- Legacy Phase 1 names are mapped to current surfaces as follows: `NexusApp` corresponds broadly to the Next.js App Router shell (`app/layout.jsx`, `app/page.jsx`); `AdminControlCenter` corresponds to authenticated role-gated dashboard views plus tenant-scoped API routes; `IntegrationManager` corresponds only to the security-control registry/preferences (`lib/security-controls.js`, `app/api/security-controls/route.js`), not live connectors. The current CSS in `app/globals.css` is the styling foundation, but a reusable component design system is not established. These are mappings, not claims that legacy modules or full acceptance requirements are implemented.
- Phase 2 middleware replaces client-supplied request IDs, passes the generated ID and start time to API handlers, and returns the ID in the response header. Structured response logs contain only event name, request ID, HTTP method, status, and elapsed milliseconds; they intentionally omit URL paths, tenant identifiers, bodies, and credentials.
- Standard JSON API responses (including authentication success/error), readiness responses, and the CSV evidence export use the response logger. Any new API route returning a custom response must also call `observeApiResponse`; this is not yet a centralized metrics backend or alerting system.
- The DPDP worker emits structured job completion/failure and maintenance-task outcomes. Worker records omit job/delivery identifiers, tenant data, webhook URLs, and exception messages; failure records include only a bounded error class. Successful periodic scans emit only when they find records, to avoid routine empty-scan log noise.
- `npm run probe:health -- <http(s)-endpoint>` provides a bounded single synthetic check for HTTP 200 and healthy PostgreSQL/Redis response fields. It is not a scheduler, monitor, alert route, or uptime measurement.
- Local probe evidence: `http://localhost:3000/api/health` returned healthy with both dependency checks true. This is a point-in-time development check only.
- An opt-in `/api/metrics` endpoint exports bounded process-local HTTP counters and duration buckets behind bearer-token authorization; host-side smoke testing verified it returns 401 without a token and Prometheus exposition with a valid token. A local-only Compose profile provisions Prometheus and Grafana; production build, 44 automated tests, dashboard JSON parsing, and Compose profile validation passed. Docker's 7.22 GB unused build cache was pruned with authorization. WSL shutdown briefly restored the existing app and healthy dependency checks, but a rebuild then failed during image-layer extraction with a read-only filesystem. Requested Recycle Bin cleanup reclaimed about 250 MB; the Windows Update download cache was already empty and its service was restarted. C: had about 72 MB free at the latest check; Redis is unhealthy and the health endpoint reported both database and Redis checks false with HTTP 503. Prometheus scraping and dashboard rendering remain unverified; containers and volumes were not removed.
- Tests establish metadata bounds and omission of request content. They do not prove log shipping, retention, access controls, dashboards, alert routing, service-level objectives, or production performance.

## Change control

Product, Security, Legal/Privacy, and Operations owners should approve or revise this roadmap before it is treated as an acceptance contract. Record approvals against a specific revision and source commit. Changes to a phase's scope or acceptance criteria require a new revision and must preserve the Phase 9 safety invariant unless a separately reviewed authorization explicitly changes it.
